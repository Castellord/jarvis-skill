# Проверка доступа к Email MCP

Используй этот сценарий, когда пользователь спрашивает, подключён ли Gmail, или перед запуском Jarvis почтовые инструменты не появились в текущей сессии.

## Предпочтительный путь

1. Используй нативный `email_accounts_list`.
2. Убедись, что он возвращает реальный аккаунт с `provider: google`, адресом и Gmail-scopes.
3. Выполни безопасный read-only запрос (`email_messages`, `action: search`) и только после успешного ответа говори, что доступ к Gmail работает.

Наличие записи в конфиге или ключа в окружении само по себе **не доказывает** доступ к ящику.

## Если почтовые MCP-инструменты не зарегистрированы

1. Сначала предложи `/reload-mcp`; если инструменты всё ещё отсутствуют — новую сессию (`/reset`).
2. Для срочной read-only проверки допустим прямой вызов **того же Email MCP** по Streamable HTTP JSON-RPC. Это не переход на IMAP/GWS/Himalaya.
3. Секрет бери только из окружения; не печатай его, не передавай в аргументах, видимых пользователю, и не сохраняй ответы с заголовками авторизации.
4. Последовательность проверки:
   - `initialize`;
   - `tools/list`;
   - `tools/call` → `email_accounts_list`;
   - `tools/call` → безопасный `email_messages/search`.
5. Считай проверку успешной только при HTTP 200, `isError: false`, реальном Google-аккаунте и успешном поисковом запросе.

### Разбор ответа прямого JSON-RPC

`tools/call` может вернуть полезный объект либо в
`result.structuredContent.result`, либо JSON-строкой в элементах
`result.content[type=text]`. Поддерживай оба варианта: сначала бери
`structuredContent`, а если его нет или он пуст, склей text-элементы и разбери
их как JSON. Пустой `structuredContent` сам по себе не означает пустой ответ.

Для Gmail `email_messages/get` поля отправителя, темы и даты находятся в
`payload.headers`, а не обязательно на верхнем уровне сообщения. При
группировке используй `threadId`; `list/search` обычно возвращает только ID,
поэтому детали нужно получать отдельным `get`.

### Счётчики Gmail: не доверяй `resultSizeEstimate`

`email_messages/search` может вернуть сильно завышенный `resultSizeEstimate`
даже при узком запросе. Это оценка Gmail, а не подтверждённое число результатов.

Для любого пользовательского отчёта:

1. Пройди все страницы через `nextPageToken` до его отсутствия.
2. Считай фактическое число элементов в объединённом массиве `messages`.
3. После получения деталей дедуплицируй по `threadId`; отдельно сообщай число
   писем и тредов, если они различаются.
4. `resultSizeEstimate` используй только как диагностическую подсказку — не
   показывай его пользователю как размер очереди и не планируй по нему операции.
5. После изменения меток повтори исходный поиск. Считай очередь пустой только
   при фактически пустом `messages` и отсутствии следующей страницы.

Минимальные заголовки для JSON-RPC POST:

```text
Authorization: Bearer $MCP_EMAIL_API_KEY
Content-Type: application/json
Accept: application/json, text/event-stream
```

Пример тела вызова инструмента:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "email_accounts_list",
    "arguments": {}
  }
}
```

## Отчёт и безопасность

- Проверка доступа — read-only: не менять метки, статус прочтения и настройки Gmail.
- В ответе показывать адрес аккаунта только если это помогает пользователю подтвердить подключение.
- Если `Jarvis/*`-меток ещё нет, отчёт классифицирует непрочитанные за период на лету и явно помечает почтовый статус как `частично`.
- Не выдавать `401` без Authorization за поломку сервера: это ожидаемый ответ публичной точки без ключа.
