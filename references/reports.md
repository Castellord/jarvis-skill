# Отчёты: один сбор данных, два рендера

Раньше здесь было два независимых контракта, которые расходились. Теперь так:
**сбор данных всегда одинаковый, различается только последний шаг — рендер.**

- Рендер `json` — когда данные запрашивает `/morning` или пользователь просит
  `/jarvis` дать данные для утренней сводки. Оформление делает `/morning`.
- Рендер `text` — когда отчёт идёт человеку: в Telegram, по расписанию, или на
  вопрос «что горит».

Выбрал рендер — придерживайся его до конца. Не смешивай: JSON без обрамляющего
текста, текст без JSON.

## Шаг 1. Сбор (общий для обоих рендеров)

Режим **read-only**, если пользователь явно не попросил разобрать почту: не
помечай прочитанным, не создавай задачи и фильтры, не меняй метки.

**Почта.** По аккаунтам из `jarvis.accounts` (пусто = все) забери письма с
меткой `Jarvis/Important` за `jarvis.digest_lookback_hours` часов. Больше
`jarvis.digest_max_items` — бери свежие. Если меток нет вообще (скилл только
поставили или провайдер их не умеет), классифицируй непрочитанные за период на
лету по `references/triage.md` и скажи об этом одной строкой в блоке статуса —
иначе цифры в отчётах будут прыгать от запуска к запуску без объяснения.

**Linear.** Через `mcp__linear__list_issues` собери задачи и прогони каждую
через `scripts/jarvis.py dates --due … --updated … --state … --tz …`. Скрипт
вернёт `overdue` / `due_soon` / `stale` / `ok` и готовую строку `detail`.
Бери только `include: true`. Ограничь суммой `jarvis.digest_max_items`,
приоритет — просроченным.

Не доверяй одному узкому фильтру, вернувшему пусто, — особенно по team/project
ID из конфига. Перепроверь запросом пошире (`assignee=me`, команда по имени,
`list_teams`) прежде чем писать «задач нет». Для `stale` явно запрашивай
in-progress статусы: отсутствие результата — это «нет данных», а не «нет задач».

### Пагинация и шум автосозданных задач

- Догружай страницы Linear до `hasNextPage: false`. Курсор бери из ответа и
  передавай в следующий вызов.
- Если очередь явно патологическая (тысячи активных issue, десятки страниц
  автодублей), допустим защитный лимит сбора. Остановись на заранее выбранной
  границе, обязательно напиши `не менее N`, поставь Linear статус `частично` и
  не называй счётчик итоговым. Не трать десятки вызовов только ради точного
  количества мусора: цель отчёта — выделить реальные действия.
- Для загруженной выборки считай две метрики отдельно: сырые записи прогони
  через `scripts/jarvis.py dates` для нижней границы общего счётчика, затем
  сгруппируй по точному заголовку и прогони представителя каждой группы для
  дедуплицированного счётчика. Не применяй дату одного представителя ко всей
  группе при подсчёте сырых записей.
- До выбора пунктов для сводки сгруппируй задачи по **точному заголовку**.
  Повторяющиеся почтовые и магазинные уведомления показывай одной строкой с
  количеством, а не как несколько отдельных срочных действий.
- Для блока «Сначала сделать» сначала рассматривай уникальные задачи с
  `Urgent`/`High`, затем сроки и последствия. Массовый дубль с более старым
  дедлайном не должен вытеснять реальную уникальную задачу по здоровью,
  деньгам, доступам или документам.
- Сохраняй два счётчика: сырой (число issue) и дедуплицированный (число точных
  заголовков). Это позволяет честно показать масштаб загрязнения очереди,
  не выдавая сотни дублей за сотни независимых обязательств.

## Шаг 2а. Рендер `json`

Только объект ниже, без markdown и без пояснений.

```json
{
  "important_emails": [
    {
      "account": "user@example.com",
      "from": "Имя Отправителя",
      "subject": "Тема",
      "reason": "Одна строка — почему это важно",
      "received_at": "2026-08-20T09:14:00Z"
    }
  ],
  "linear_summary": [
    {
      "title": "Название задачи",
      "project": "Проект",
      "status": "overdue|due_soon|stale",
      "detail": "Просрочено на 3 дня",
      "url": "https://linear.app/…"
    }
  ],
  "status": {"mail": "ok|partial|error", "linear": "ok|partial|error"}
}
```

Пусто — пустые массивы. Не выдумывай задачи и не занижай просрочку.

## Шаг 2б. Рендер `text`

Если нового нет и задание допускает тихую доставку — верни ровно `[SILENT]`.

```markdown
## Jarvis — <дата, время>

### Почта
- Важных: **N**, задач заведено: **M**, шума: **K**.
- **<Отправитель / тема>** — почему важно.
- **<Отправитель / тема>** — почему важно.

### Linear
- Просрочено: **N**, горит на неделе: **M**, зависло: **K**.
- **<ID / название>** — <detail из скрипта>.
- **<ID / название>** — <detail из скрипта>.

### Сначала сделать
1. **<действие>** — почему сейчас.
2. **<действие>** — почему сейчас.
3. **<действие>** — почему сейчас.

### Статус
- Почта: <ok / частично / ошибка>
- Linear: <ok / частично / ошибка>
```

Правила рендера:

- Одна короткая строка на пункт. Длинное обоснование убивает смысл сводки.
- Блок `Статус` показывай, **только** если что-то не ok. Всё в порядке —
  выброси его целиком, не занимай место.
- Пустой блок — прямая фраза: `- Нового важного нет.` / `- Просроченных нет.`
- Источник недоступен — одна честная строка, без выдуманных данных.
- Шум не перечисляй пописьменно, только счётчиком.
- Много одинаковых сгенерированных задач в проекте — скажи об этом одной
  строкой вместо того, чтобы залить ими отчёт.
- Никаких имён MCP-тулов, cron-boilerplate и советов по настройке, если не
  просили диагностику.

## Шаг 3. «Сначала сделать»

3–4 пункта, отсортированные по срочности и последствиям. Приоритет: реальные
сроки → риски по деньгам, доступам и здоровью → блокеры для других людей →
всё остальное. Каждый пункт — конкретное действие, а не тема. Пунктов меньше
трёх — это нормально, добивать до трёх выдуманным не надо.
