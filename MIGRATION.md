# Переход с 1.0.0 на 2.0.0

## Что делать при обновлении

1. Заменить каталог скилла целиком. Старый `assets/state.yaml`, если он успел
   появиться, можно удалить — он больше не используется.
2. Убрать из `config.yaml` ключи `skills.config.jarvis.default_team` и
   `jarvis.default_project`: теперь дефолты живут только в
   `assets/routing-rules.yaml`, секция `defaults`. Ключ `jarvis.label_scheme`
   переименован в `jarvis.label_prefix`.
3. Зарегистрировать `/jarvis` в Telegram-гейтвее **без обязательных
   аргументов** и проверить, что команда реально попала в список бота.
4. Прогнать `python3 scripts/jarvis.py selftest` — должно быть 16 из 16.
5. Первый запуск сделать вручную (`/jarvis` → «разобрать почту») до включения
   cron: он проставит метки на текущей почте, и станет видно качество правил.

## Что изменилось по существу

| Было | Стало |
|---|---|
| `state.yaml` + `last_seen` | метки `Jarvis/Processed` и др. в почте |
| дедуп поиском `message_id` в описаниях issue за 30 дней | метка `Jarvis/Task` на треде + attachment `jarvis://mail/<id>` |
| team/project в конфиге **и** в YAML | только в YAML, секция `defaults` |
| `digests.md` + `user-facing-reports.md` | один `reports.md`: общий сбор, два рендера |
| `classification.md` + `routing.md` | один `triage.md` |
| `gmail-filters.md` | вошёл в `feedback.md` |
| мастер из 6 шагов | ноль обязательных вопросов на первом запуске |
| фидбек только «это шум» | грамматика из 7 формулировок |
| письмо = единица разбора | тред = единица разбора |
| даты и матчинг правил прозой | `scripts/jarvis.py` |
| `confirm_before_issue` отсутствовал | есть, по умолчанию `true` |

## Что проверить в первую неделю

- Не появились ли дубли задач по одному треду.
- Не уехало ли что-то важное в `Jarvis/Noise` — просмотри метку глазами.
- Совпадают ли цифры «просрочено на N дней» с Linear на границе суток
  (это проверка таймзоны в `jarvis.timezone`).

# Переход с 2.1.2 на 2.2.0

Обратно совместимо: формат `routing-rules.yaml` читается старый, переписывается
новый. Ручных действий не требуется, кроме п.3.

## Что делать при обновлении

1. Заменить каталог скилла. `assets/routing-rules.yaml` **не трогать** — он
   теперь в `.gitignore` и принадлежит установке, а не репозиторию.
2. Прогнать `python3 scripts/jarvis.py selftest` — должно быть 38 из 38
   (число проверок теперь считается, а не захардкожено).
3. Проверить `privacy` у категорий, где письма содержат чувствительные данные:
   в поставке `health` переведена в `strict`, у своих категорий проставь сам.
4. Первый прогон разбора сделать вручную: писем, доходящих до уровня 3, стало
   больше — это ожидаемо, см. ниже.

## Что изменилось по существу

| Было | Стало |
|---|---|
| совпадение по `routing` = вердикт `route`, задача заводится без LLM | подсказка `suggested_*` при `unresolved`; судьбу решает уровень 3 |
| терминальность правила нельзя отключить | опт-ин `terminal: true` в категории |
| `note` писался комментарием и терялся при следующей записи | `note` — поле YAML, переживает перезапись |
| дефолтный путь к правилам — относительный, от cwd | от каталога скрипта; `match` возвращает `rules_path` и `rules_found` |
| `2026-09-05` разбиралась как UTC-полночь | как календарная дата |
| `stale` только для статусов `in progress`/`started` | по `statusType: started`, имя статуса — фолбэк |
| `checks_run` захардкожен (22 при 24 проверках) | считается фактически |

## Чего ждать после обновления

Уровень 2 больше не закрывает письма, попавшие в `routing`. Расход на LLM
вырастет, зато перестанут появляться задачи из рассылок, поймавшихся на широкое
ключевое слово (`подписка`, `счёт`, `оплата`). Если по какой-то категории
совпадение действительно всегда означает действие — верни ей терминальность
точечно:

```bash
python3 scripts/jarvis.py add-route --category <key> --terminal
```

## Что проверить в первую неделю

- Не выросло ли число `important` за счёт того, что раньше молча становилось
  задачей.
- Совпадают ли «просрочено на N дней» с Linear, если таймзона западнее UTC
  (именно там был off-by-one).
- Появляются ли в сводке зависшие задачи со статусами вроде `In Review` —
  раньше они не детектировались вовсе.

# Переход с 2.2.0 на 2.2.1

Только документация, скрипт не менялся. Заменить каталог скилла, `selftest`
прогонять не обязательно (38/38 без изменений).

## Что чинится

One Job задавал `Что делаем с этой задачей?` без названия задачи, статуса и
ссылки. Причина: контекст выводился прозой **до** вызова `clarify`, а
Telegram-гейтвей сворачивает такой текст в служебный блок с тул-колами — до
пользователя доезжает только сам вопрос с кнопками.

Теперь `references/one-job.md` требует собирать контекст **внутри текста
вопроса** по шаблону (ID, заголовок, статус/приоритет/дедлайн/проект, причина
выбора, описание, ссылка), с ограничением по длине под одно сообщение Telegram.
То же правило распространено на остальные вопросы режима: «на когда
переносим», «выполнено или отменяем», «какой ближайший шаг» — все называют
задачу.

Общее правило добавлено в раздел «Стиль» SKILL.md: любой вопрос пользователю
самодостаточен, потому что прозаический текст перед вызовом инструмента может
не дойти.

## Что проверить

Запустить `/jarvis` → пункт 3 и убедиться, что в сообщении с кнопками есть ID,
заголовок и ссылка на задачу.
